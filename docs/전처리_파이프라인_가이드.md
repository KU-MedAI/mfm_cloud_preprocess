# MFM WGS–RNA 전처리 파이프라인 가이드

이 문서는 `/NHNHOME/korea/mfm_data/process_code/v2`의 현재 production 계약을 설명한다.
`/NHNHOME/korea/post-training/processing_code`는 RNA 최신 구현을 대조한 참고본이며 수정하지 않았다.

## 최신 모드와 실행 기준 · 2026-11-23

- 현재 실행·JSON·자원·정리 설정은 [GUIDE](../GUIDE.md)를 우선함. 아래 pilot 상태와 날짜별 결과는 당시 기록임.
- `full`은 HAP readset, `sequence_only`는 HAP 서열, `pileup_feature`는 서열+reference pileup임. WGS-only/coverage_only의 기본 pileup은 Stage10 개인 HAP 재정렬을 하지 않음. reference 정렬 BAM의 관측을 chain으로 HAP 좌표에 투영함.
- RNA full의 WGS 변이 검증·ASE·CNV는 WGS 출력과 별개로 read 근거가 필요함. coverage_only는 HAP1/2 RNA1bp signal/QC를 처리하고20–23은 비적용으로 기록함. RNA 보류와 coverage_only는 동시에 설정하지 않음.
- `MFM_PILEUP_BENCHMARK_REALIGN=1`은 재정렬 비용을 더하는 실측 전용 옵션임. 기본 pileup 비교에 사용하지 않음. 자원 예시는 고정16CPU×4/공유68·RAM1.65TB/예약1.485TB이며, 실제 작은 한도를 우선함.
- 모델 전용 정리 후 FASTA/BAM은 제거될 수 있음. 최종 서열·feature·signal·주석·압축 chain·QC·metadata·로그를 보존함. 내부/외부 원본 정리 설정은 [정리 정책](../GUIDE.md#7-검증재개정리)을 따름.

## 4. Stage 02에서 RNA까지 먼저 검사하는 이유

RNA pair manifest가 있으면 Stage 02에서 다음을 검사한다.

- BAM/CRAM과 index 존재, `samtools quickcheck`
- CRAM decode reference와 `.fai`
- header의 autosome과 sort order
- `@RG SM`이 sample ID 또는 허용 public alias인지
- 전체 record와 paired record 비율(기본 0.90 이상)
- GTF 존재와 content hash

결과는 `<sample>/qc/rna_preflight.json`에 입력 inode/size/mtime와 함께 동결된다. Stage 13은
비싼 검사를 반복하지 않고 입력이 같은 파일인지 확인한다. Stage 02에서 문제가 난 sample은
그 sample만 실패 처리되며 cohort runner는 다음 sample을 실행한다.

## 5. WGS 재정렬과 window 좌표

개인 HAP 좌표는 GRCh38 숫자 좌표와 같다고 가정하지 않음. Stage09 chain과 reference/HAP 계약으로 연결함. full 또는 RNA full의 WGS 근거에서는 Stage10 재정렬을 수행하고 Stage11이 두 HAP CRAM/index/QC를 확인함. 기본 pileup은 Stage10 대신 reference alignment/HAP FASTA/chain 입력을 검증하며, sequence_only는 서열 계약을 사용함. mapped-fraction은 해당 재정렬 경로에서 기본 record_only, strict 명시 때만 하한을 적용함.

Illumina는 paired FASTQ semantics와 base quality를 보존해 BWA-MEM2로 정렬한다. HiFi는
긴 read·긴 indel 특성 때문에 minimap2를 사용한다. HAP-specific mode에서는 양 HAP 상대 score와
phase evidence를 이용하며 동점·비정보성 read는 unknown으로 남긴다. `all_to_both` mode는 coverage
보존용이며 두 HAP 값을 서로 독립 sample처럼 합산하면 안 된다.

## 6. RNA window와 duplicate 정책

Stage 18은 HAP별 전장 chromosome array를 `coverage.zarr`에 저장한다. 같은 실행 안에서 Stage 11
`windows.tsv`를 HAP별 `kept=1`로 필터한 행 순서 그대로 `window_key`, `offsets`, flat `depth`를
`coverage_windows.zarr`에 저장한다. 두 번째 `samtools depth`는 실행하지 않는다. RNA Stage 25는 다음을 전부 확인한다.

- RNA `window_key`와 WGS window key의 값·순서가 완전히 동일
- `offsets[-1] == len(depth)`
- `windows.tsv` SHA-256 일치
- schema가 `mfm_rna_window_coverage_v1`
- 전장 contig별·window flat raw uint32 depth의 실제 SHA-256, total depth, nonzero 위치 수가 producer metadata와 일치

RNA Picard MarkDuplicates는 duplicate flag와 metrics를 만들지만 BAM에서 read를 물리적으로
삭제하지 않는다. dense coverage는 GTEx 방식으로 duplicate를 포함하고, ASE count는 Castel/AlleleSeq
계열 QC 목적상 duplicate를 제외한다. 이렇게 하면 한 파일에서 목적별 정책을 재현할 수 있다.

## 7. 최종 검증과 cleanup

WGS-only Stage 23과 RNA pair Stage 25가 확인하는 핵심 항목은 다음과 같다.

- sample 디렉터리명과 `metadata/sample.json` ID 일치
- 요청한 모든 autosome에 HAP1/HAP2 window 존재, key 중복 없음
- compact manifest `complete`, `full`, 모든 contig PASS
- 독립 source trace PASS, compact root/contig 일치, trace 이후 변경 없음
- WGS/RNA preflight의 schema/sample/status PASS
- WGS Stage 01–12와 RNA Stage 13–25의 success 또는 명시적 conditional skip, success 단계 log 존재
- HAP1/HAP2 FASTA·FAI·chain과 personal FASTA QC의 요청 contig 전체 무결성
- Stage 09 `permanent_assets.json`과 현재 HAP FASTA·FAI·chain SHA-256 일치
- pair에서는 lifted GTF/exon, RNA realign QC와 두 RNA Zarr 계약을 확인함. RNA full에만 ASE sidecar/CNV/QC를 추가 요구함
- RNA full의 Stage21 count4종/Stage22 CNV/Stage23 ASE input의 SHA-256 producer→consumer 연결을 확인함. coverage_only는signal manifest·지문을 사용함

결과는 `qc/final_package_validation.json`과 `metadata/completeness.tsv`에 기록한다. 보고서의 schema/revision과 현재 payload 계약을 확인함. WGS-only Stage 24와 RNA pair Stage 26은 해당
JSON의 schema/revision/sample/mode/status, 영구 HAP asset manifest hash와 현재 RNA evidence hash·수정시각을 다시 확인하며 PASS가 아니면 어떤 파일도 삭제하지 않는다.
WGS–RNA pair는 RNA까지 끝난 후 한 번만 cleanup하고 WGS-only는 WGS 검증 직후 cleanup한다.

독립 cohort utility인 Stage 27 실행 예시는 다음과 같다.

```bash
./run_pipeline.sh catalog /path/to/output --expected-samples 3212
```

`catalog/sample_catalog.tsv`에는 PASS sample만 들어간다. 실패/미완료 sample은
`catalog/incomplete_samples.tsv`, project별 수는 `catalog/cohort_summary.tsv`에 남는다.

## 10. read 수와 depth 정규화 결정

전처리 단계에서는 platform별 read 수나 depth를 강제로 같게 만들지 않는다. 같은 read 수는
Illumina와 HiFi에서 염기 수·오류 구조·정보량이 다르고, 사전 downsampling은 복구할 수 없기 때문이다.
대신 native read/depth, retained fraction, primary/supplementary/duplicate 비율을 QC에 보존한다.
모델 비교에서 같은 depth가 필요하면 원본 compact는 유지하고 dataloader 또는 별도 deterministic
ablation에서 seed와 목표 coverage를 명시해 downsample한다.
