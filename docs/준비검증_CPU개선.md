# 준비·생산·검증의 고정16CPU 활용 개선

## 적용 범위
- 2026-11-25의 후속 개선이며 DNA pileup tensor 36채널과 RNA full의 값·필터·ASE/CNV·좌표 정책을 유지한다. 기존 결과를 덮어쓰거나 재배열하지 않는다.
- CPU16은 계산 배분 상한이다. 실제 affinity/cgroup/Slurm 한도가 더 작으면 우선한다. 자식 HAP에는 부모 lease와 자식 예산 중 작은 값을 적용한다. CPU/RAM 예약과 실제 사용량은 따로 기록한다.

## BAM·CRAM 준비
- CRAM의 flag/HP/PS 통계를 HTSlib 단일 읽기로 계산한다. 기존 samtools 3회 집계와 같은 카운트를 검사했다. native 도구가 없는 auto 환경은 기존 경로로 돌아가며 손상 입력은 정상 결과로 처리하지 않는다.
- 같은 읽기에서 실제 reference·position·reverse 순서를 확인한다. 헤더에 coordinate라고 적혀 있는 것만으로 정렬을 생략하지 않는다.
- 헤더와 전체 순서가 모두 맞는 CPU 입력만 재sort 없이 BAM으로 변환한다. 원본/인덱스는 수정하지 않고, 입력 지문·출력 통계·색인·최종 검증을 유지한다. 알 수 없는 순서나 거짓 헤더는 기존 sort로 처리한다.
- 해독/I/O/메인 스레드를 같은 CPU 예산에 포함한다. reference FAI의 최대 길이와 해독 대기 버퍼 수로 RAM을 계산하고10%여유를 예약한다. 실제 RSS가 사전계획을 넘으면 실패한다.

## Pileup 생성과 독립 검증
- HAP별 배열 순서로 쓰는 경우 생산 버퍼를 저장 dtype과 C순서 바이트로 해시한다. SHA를 만들기 위한 별도 전체 재읽기를 줄인다.
- 순서가 맞지 않는 window 입력은 기존 저장 배열 재읽기 방식을 유지한다.
- 독립 HTSlib source 검증은 실제 저장 배열 전체를 계속 읽어 원본과 대조한다. 이전36채널/12채널 읽기·재개와 변조 거부를 유지한다.

## RNA duplicate 표시
- Picard와 기존 GTEx duplicate 인자/flag/metrics를 유지한다. 임시 BAM의 무손실 압축 수준만1로 낮추며 cache 근거에 기록한다. 압축 수준5와 동일한 모든 정렬 레코드를 비교한다.
- 생성이 끝난 임시 BAM의 색인과 독립 primary/duplicate QC를 할당 안에서 함께 수행한다. CPU가 작으면 기존처럼 순차 실행한다.
- 부모 관리1CPU와 색인·QC의 worker/I/O 스레드를 합산한다. 새 BAM·색인·QC가 모두 성공한 뒤 기존의 원자적 게시를 수행한다.

## 검증·정리
- source trace 시각을 파일마다 다시 stat하지 않고 검사 시작/종료에 확인한다. 파일 목록/mtime은 현재 DirEntry로 읽으며 외부 디렉터리 링크를 내려가지 않는다. 파일 링크의 대상 검사와 삭제 전후 독립 검증은 유지한다.
- trace가 검사 중 바뀌면 실패한다. 과거 PASS나 용량 cache를 삭제 승인 근거로 사용하지 않는다.

## 성능 해석
- I/O 대기와 도구의 직렬 알고리즘까지 모든 순간16코어 사용을 보장하지 않는다. 실제 평균 CPU·경과시간·RSS·읽기/쓰기량으로 효과를 평가한다. CPU 사용률을 높이기 위한 불필요한 계산은 추가하지 않는다.
- 소형/부분 시험을 전체 donor 속도나 Short pair의 Azure 완료시간으로 환산하지 않는다. 새 전과정 실측 전에는 기존9.9시간과 최신 코드 예상시간을 구분한다.

## 부분 비교 결과
- 합성 150bp read 500만 개의 CRAM(412MB)을 사용해 통계와 BAM 변환만 기존→개선→개선→기존 순서로 비교했다. 두 실행 모두 affinity와 예산은16CPU였다. OS 캐시를 비우지 않았으며 검증 시간은 타이머에서 제외했다.
- 기존 평균3.460초·실제 평균6.111코어, 개선 평균1.350초·실제 평균8.515코어였다. 네 출력의 모든 해독 레코드와 flag/HP/PS 통계가 같았다. 개선 출력은 무손실 압축 차이로 약1.75% 컸다.
- 짧은 합성 시험에서 불필요한 sort 제거 효과를 확인한 결과다. 실제 donor의 준비시간·전체시간·Azure 성능을 입증하는 자료는 아니다. 50만 read 시험에서는 유의한 속도 차이를 판단할 수 없었다.
