# MFM v2 단계별 입력·기능·출력 상세

기준일: **2026-11-23**. `/NHNHOME/korea/mfm_data/process_code/original`의 WGS01–12/23–24, RNA13–26, catalog27을 설명함. 실제 분기는 `run_wgs_sample.sh`, `run_rna_sample.sh`, `config_v2.sh`를 기준으로 함. 실행·자원·정리 JSON은 [GUIDE](../GUIDE.md)를 먼저 확인함.

## 최신 출력 모드에 따른 적용 범위

| 항목 | full/readset | sequence_only | pileup_feature |
|---|---|---|---|
| HAP 서열·chain·window | 적용함 | 적용함 | 적용함 |
| WGS01/02/06 read 준비·검증·haplotag | 적용함 | RNA full 근거가 필요할 때 적용함 | 적용함 |
| WGS10 개인 HAP 재정렬 | 적용함 | WGS-only/coverage_only 비적용임 | WGS-only/coverage_only **비적용임** |
| WGS12 최종 입력 | 서열·readset·HAP depth | 서열 | 서열·reference pileup tensor |
| RNA full ASE/CNV 근거 | 필요함 | temporary WGS 정책 명시 후 처리함 | 별도 WGS 근거/개인 HAP CRAM 처리함 |

`MFM_PILEUP_BENCHMARK_REALIGN=1`은 별도 실험에서 Stage10을 강제하는 옵션임. 기본 pileup은0이며 이 모드의 feature는 Stage06 reference BAM에서 계산함. 개인 HAP CRAM을 pileup source로 사용하지 않음.

아래 readset/CIGAR·HAP 정렬 상세는 **full 경로 기준**임. sequence/pileup의 대체 입력은 해당 단계의 모드 설명을 우선함. RNA coverage_only는20–23 비적용, RNA 보류는RNA branch 전체 비적용이며, 해당 모드에 맞춰 최종 검증함. 모델 전용 정리 후 물리 FASTA/BAM이 항상 남는다고 가정하지 않음.

## 1. 경로 표기와 실행 흐름

문서에서 사용하는 약어는 다음과 같다.

- `S`: sample ID
- `F`: sample final root = `<output-root>/<wgs|wgs_rna_pair>/<project>/<S>`
- `W`: sample work root = `<output-root>/_work/<run-id>/<data-group>/<project>/<S>`
- `P`: sample별 VCF 디렉터리
- `R`: RNA final root = `F/rna_personal/<phase-mode>`
- `<layout>`: 기본 compact layout 이름
- `<mode>`: `HAP_READ_MODE` (`all_to_both`, `hp_routed_with_unknown`, `hap_specific`)

실제 큰 흐름은 다음과 같다.

```text
00 환경 검사
  ↓
01 입력 WGS를 canonical BAM으로 표준화
  ↓
02 WGS·VCF·reference·RNA 원본 preflight
  ↓
03 VCF 준비 → 04–05 Clair3(opt-in) → 06 haplotag
  ↓
07–08 de novo(opt-in) → 09 HAP FASTA/chain
  ↓
10 WGS HAP 재정렬(필요한 모드만) → 11 windows → 12 선택 payload Zarr
  ↓ (WGS–RNA pair만)
13 RNA FASTQ → 14 GTF lift → 15 STAR index → 16 STAR 정렬
  ↓
17 MarkDuplicates → 18 RNA coverage → 19 RNA QC
  ↓
20 WGS 검증 HAP variant → 21 allele count → 22 CNV → 23 ASE QC (RNA full만)
  ↓
24 RNA metadata → 25 최종 패키지 검증 → 26 cleanup
  ↓
27 cohort catalog
```

한 sample 내부에서 검증이 실패하면 즉시 그 sample을 중단한다. sample-list runner는 실패 상태와 log를 남기고 다음 sample을 계속 실행한다.

## 2. 공통·WGS 단계

## 00_environment.sh — 실행 환경 설치·검증

**실행 성격**

- sample 데이터 처리 단계가 아니라 실행 환경 점검 단계다.
- 인수 없이 실행하면 `environment.yml`, `requirements.txt`, `clair3_environment.yml`로 core·RNA·denovo·Clair3 도구를 설치·보강하고 버전 표를 갱신한다.
- production 전에는 `verify-core`, RNA branch 전에는 `verify-rna`를 사용한다.
- `verify-*`와 `print`는 설치 없이 확인한다. `setup`·`install-*`은 conda 환경을 변경하므로 실행 중인 공유 작업이 끝난 뒤 실행한다.

**Input**

- `config_v2.sh`의 tool 경로와 conda 환경 설정
- core reference FASTA 경로
- 환경 선언 파일과 설치 후 생성되는 `TOOL_VERSIONS*.tsv`의 버전 목록
- 명령: `verify`, `verify-core`, `verify-clair3`, `verify-rna`, `verify-denovo`, `install-*`, `print`

**Function**

- `jj_mfm` Python과 `pysam`, `zarr`, `numcodecs`, `numpy`, `pandas` import를 검사한다.
- core tool은 bcftools, samtools, minimap2, BWA-MEM2, WhatsHap, Picard를 검사한다.
- RNA tool은 STAR, Picard, bedtools, samtools, pyBigWig를 검사한다.
- opt-in 분기용 Clair3 env와 hifiasm을 별도로 검사한다.

**Validation / stop**

- 필요한 실행 파일, Python package 또는 reference가 하나라도 없으면 nonzero로 종료한다.
- 자동 fallback으로 다른 aligner를 선택하지 않는다.

**Output**

- `verify-*`: stdout/stderr의 버전·경로 보고만 생성한다.
- `install-*`: 지정 conda env에 package를 설치한다. sample 산출물은 없다.

**Next**

- 환경 검증을 통과한 뒤 Stage 01을 시작한다.

## 01_prepare_analysis_bam.sh — WGS 입력을 canonical BAM으로 표준화

**Input**

- 실행 manifest의 `alignment_path` 또는 `read_files_manifest`
- 지원 형식: aligned BAM, uBAM, CRAM, FASTQ/FASTQ.gz, 여러 run
- `source_decode_reference_fasta`: CRAM decode용 exact reference
- `analysis_reference_fasta`: raw read 재정렬용 reference
- sample ID, platform, read type, read group 정보

**Function**

- 입력 계약을 JSON으로 동결한다.
- aligned BAM은 검증 후 coordinate sort/index를 고정한다.
- CRAM은 exact decode reference로 BAM으로 변환한다.
- Illumina raw FASTQ/uBAM은 기본 BWA-MEM2 `mem -Y`로 정렬한다.
- HiFi/ONT/CLR raw read는 minimap2의 platform preset으로 정렬한다.
- SEQ와 base quality를 보존하고 모든 downstream 입력을 BAM 하나로 통일한다.
- Illumina duplicate 정책 `auto`는 신뢰 가능한 Picard/GATK provenance가 있으면 기존 0x400 flag를 보존하고, 없으면 Picard MarkDuplicates를 실행한다. `REMOVE_DUPLICATES=false`이므로 read를 삭제하지 않는다.

**Validation / stop**

- aligned/unaligned 입력 혼합, paired FASTQ의 R1/R2 누락, reference 누락을 거부한다.
- coordinate sort, index, `@SQ`, `@RG SM`, SEQ/QUAL을 검사한다.
- 변환 전후 record, primary/secondary/supplementary, HP/PS, duplicate 수 계약을 검사한다.
- canonical 출력 확장자는 반드시 `.bam`이어야 한다.

**Output**

- `W/prepared_input/S.input_contract.json`: 입력 파일·format·reference 계약
- `W/prepared_input/S.analysis.bam` 및 `.bai`: canonical analysis BAM
- Stage 01 QC JSON(`sample_stage04_qc` 경로): 변환 방식, reference fingerprint, record 대조, duplicate provenance/metrics
- `W/logs/04_contract.log`
- `W/logs/04_prepare_alignment.log`

**Next**

- Stage 02는 canonical BAM과 Stage 01 QC를 함께 검사한다.

## 02_preflight.sh — WGS·reference·VCF·RNA 입력 계약 검사

**Input**

- Stage 01 canonical BAM과 index/QC
- decode reference 및 sequence/VCF reference와 각 `.fai`
- Illumina: chr1–22 phased panel VCF와 `.tbi`
- long read public branch: public VCF, index, donor ID, callset, phase source
- WGS–RNA pair: RNA BAM/CRAM, RNA index/reference, GENCODE GTF
- manifest의 platform/read type/dataset role와 출력 root

**Function**

- tool, manifest, sample ID, alignment, reference, VCF, RNA, disk 계약을 **WGS 처리 시작 전에** 검사한다.
- canonical BAM의 `samtools quickcheck`, index, `@RG SM`, base quality를 검사한다.
- chr1–22 각각에서 alignment header, decode FASTA, sequence FASTA의 길이를 대조한다.
- alignment `@SQ M5`와 decode FASTA MD5를 chr1–22 전부 대조한다. Stage 01 exact-reference provenance가 있는 BAM은 M5 생략을 허용한다.
- Illumina CRAM/BAM은 대표 영역 decode도 검사한다.
- 각 VCF를 모든 autosome에서 `bcftools norm --check-ref e`로 sequence reference와 대조한다.
- panel/public VCF에 donor sample이 실제 존재하는지 확인한다.
- RNA pair는 RNA `quickcheck`, index, CRAM decode reference, header/SM, paired fraction(기본 0.90 이상), GTF를 검사하고 source inode/size/mtime을 동결한다.
- 출력 filesystem의 최소 여유 공간을 검사한다.

**Validation / stop**

- reference, VCF, BAM/CRAM, RNA 중 하나라도 FAIL이면 해당 sample은 여기서 종료한다.
- sample-list 실행은 다음 sample로 계속한다.
- Illumina는 Stage 01 duplicate provenance가 없거나 metrics가 불완전하면 실패한다.

**Output**

- status root의 `preflight/S.preflight.tsv`
- status root의 `preflight/S.preflight.json` (`mfm_preflight_qc_v2`)
- `F/qc/wgs_preflight.tsv`
- `F/qc/wgs_preflight.json`
- pair인 경우 `F/qc/rna_preflight.json`: RNA source fingerprint와 검사 결과
- reference/VCF 검증 cache와 오류 log

**Next**

- PASS sample만 Stage 03으로 진행한다. Stage 13은 `rna_preflight.json`의 source fingerprint를 재검증한다.

## 03_prepare_vcf.sh — sample별 sequence/tag VCF 준비

**Input**

- Illumina: 1KGP high-coverage phased panel 또는 선택적으로 미리 만든 common VCF
- long read: manifest의 하나 이상 public VCF, donor ID, exact VCF reference, callset, `phase_source=provided`
- sequence variant policy(기본 SNV+indel), chr1–22
- Clair3 opt-in sample은 이 단계에서 VCF 생성을 미룬다.

**Function**

- Illumina는 panel에서 sample을 추출하고 chromosome별 결과를 합쳐 두 VCF를 만든다.
- public long read는 donor subset, 정규화, multiallelic 분해, SNP/indel 제한, phased genotype을 검증한다.
- `seq.vcf.gz`는 개인 HAP FASTA 생성용이다.
- `tag.vcf.gz`는 WhatsHap HP/PS 부여용이다.
- `CREATE_COMMON_VCF=1`일 때만 cohort common VCF를 먼저 생성한다.

**Validation / stop**

- 지원 source는 short read `illumina_panel`, long read `public|clair3`뿐이다.
- public branch는 donor/reference/callset/phasing 오류 시 중단하며 Clair3로 자동 fallback하지 않는다.
- Illumina `tag.vcf.gz`는 모든 record의 GT를 끝까지 읽는다. 허용값은 완전한 diploid phased heterozygous인 `0|1` 또는 `1|0`뿐이다. `0/1`, `1/0`, `.|1`, `1|.`, `./.`, homozygous·다배수 GT가 하나라도 있으면 해당 sample의 Stage 03만 실패한다. HAP1/HAP2 방향을 정하는 구조적 계약이므로 `SAMPLE_VCF_FAST_VALIDATE=1`이어도 이 검사는 생략하지 않는다.
- tag VCF index의 record 수와 실제 조회한 GT 수가 같아야 한다. 검사 결과는 complete-phased, unphased, missing, other, homozygous count로 summary TSV에 남긴다.
- 필수 VCF와 index/source JSON 생성 여부를 확인한다.

**Output**

- `P/S.seq.vcf.gz` 및 `.tbi`
- `P/S.tag.vcf.gz` 및 `.tbi`
- public/Clair3 계열은 `P/S.seq.vcf.source.json`
- 선택 시 cohort common VCF와 concat work 파일
- `*.persample_vcf.summary.tsv`와 `*.persample_vcf.metadata.json`: tag GT 전수 검사 수치와 `all_records_exactly_0|1_or_1|0` 계약

**Next**

- 일반 production은 Stage 06으로 간다. Clair3 opt-in sample만 Stage 04–05를 거친다.

**Function**

**Output**

## 06_haplotag.sh — WGS read에 HP/PS tag 부여

**Input**

- Stage 01 canonical BAM
- Stage 03 `tag.vcf.gz`, index, exact decode reference
- Clair3 branch는 Stage 04의 haplotagged BAM을 재사용

**Function**

- Illumina는 panel phased VCF, long read production은 public phased VCF로 WhatsHap haplotagging을 수행한다.
- supplementary segment에도 tag를 전달한다.
- read를 HAP1/HAP2에 재정렬하기 전에 기존 phase evidence를 고정한다.

**좌표와 태그의 의미**

- 원본 reference 좌표 BAM, 같은 reference의 phased VCF 및 FASTA를 사용한다. WhatsHap은 phased allele 지지를 보고 HP/PS를 부여한다. 변이 주변의 국소 재정렬과 Stage 10의 전체 개인 HAP 재정렬은 다른 작업이다. [WhatsHap 공식 설명](https://whatshap.readthedocs.io/en/latest/guide.html#whatshap-haplotag-tagging-reads-by-haplotype).
- Stage 10 CRAM에는 원래 VCF를 그대로 적용할 수 없다. indel로 POS가 달라질 수 있고, 개인 FASTA에 변이가 이미 반영되어 REF도 달라질 수 있다. 예: 원본 VCF의 `C>T`, `GT=0|1`에서 HAP2 기준 염기는 T이므로 `REF=C`를 그대로 사용하면 기준이 맞지 않는다.
- 후행 haplotagging은 원리상 가능하지만 HAP reference 기준의 POS·REF/ALT·indel·GT/phase 표현과 read 귀속 검증이 필요하다. chain은 이 조건을 자동으로 충족시키지 않는다. 기존 HP를 미리 요구하는 routing도 재설계해야 하므로 현재 단계를 단순 교환하지 않는다.
- Stage 10의 HP/PS는 선행 판별 정보를 운반한 것이다. 정렬 대상 HAP 번호와 HP 번호는 서로 다른 정보다. PS도 개인 HAP 위치가 아니라 원본 phase-set 식별 의미를 유지한다.

**Validation / stop**

- long read public branch는 `--allow-longread-vcf-haplotag`을 명시한 경로만 허용한다.
- VCF/index/source JSON과 alignment/index가 없으면 중단한다.

**Output**

- `F/haplotagged/S.illumina.hg38.haplotagged.bam` 또는 long-read public/Clair3 대응 alignment와 index
- 같은 디렉터리의 `S.haplotag.summary.tsv`
- 같은 디렉터리의 `S.haplotag.metadata.json`

**Next**

- 일반 VCF-consensus 경로는 Stage 09로 간다. de novo opt-in은 Stage 07–08을 거친다.

## 07_denovo_assembly.sh — long-read de novo assembly (opt-in)

**실행 조건**

- long read이고 `SEQUENCE_SOURCE=denovo`인 연구 분기만 실행한다.

**Input**

- canonical long-read alignment, reference, 대상 contig, platform, hifiasm 설정

**Function**

- 지정 contig read를 FASTQ로 추출하고 hifiasm을 실행한다.
- GFA를 FASTA로 변환하고 contig 수, 총 염기, N50, hap/primary 후보를 기록한다.
- 임의 contig를 HAP1/HAP2 chromosome으로 자동 승격하지 않는다.

**Validation / stop**

- assembler 결과 GFA/FASTA와 최소 contig 길이를 검사한다.
- 실패 sample은 summary에 FAIL로 기록하고 종료한다.

**Output**

- `F/denovo_assembly/<label>/reads/`
- `F/denovo_assembly/<label>/assembly/`
- `F/denovo_assembly/<label>/fastas/`
- `F/denovo_assembly/<label>/logs/`
- `F/denovo_assembly/<label>/denovo_assembly_qc.json`
- final-root 수준 cohort summary/metadata TSV·JSON

**Next**

- Stage 08 anchoring QC. 현재 자동 promotion이 없으므로 일반 production HAP FASTA 경로로 이어지지 않는다.

## 09_personal_fasta.sh — HAP1/HAP2 FASTA와 chain 생성

**Input**

- 기본 경로: Stage 03/04 `S.seq.vcf.gz`와 exact sequence reference
- assembly-direct 경로: HAP1/HAP2 assembly FASTA, `.fai`, chromosome alias, 선택적 official chain, phase label status
- chr1–22, SNV+indel policy

**Function**

- 기본 경로는 `bcftools consensus -H 1/-H 2 --chain`으로 두 개인 HAP FASTA와 reference→HAP chain을 생성한다.
- invalid base를 sanitize하고 FASTA index를 만든다.
- chain 방향, reference/HAP fingerprint, contig 길이를 QC에 기록한다.
- Stage 09 완료 시 보존 대상 FASTA·FAI·chain·QC의 크기와 SHA-256을 `permanent_assets.json`에 고정한다. 이후 final validation과 cleanup은 이 기준점을 재생성하지 않고 현재 파일과 대조한다.
- assembly-direct는 제공 assembly/alias/chain을 표준 디렉터리 구조로 검증·배치한다.

**Validation / stop**

- seq VCF/reference/phase 정보가 없으면 중단한다.

## 11_windows.sh — HAP 개인 좌표 1 MiB window 생성

**모드 분기**: Stage10이 필요한 경로에서만 두 개인 HAP CRAM/index/QC를 요구함. 기본 pileup은 HAP FASTA/chain과 reference 정렬 입력의 길이·서열·index 계약을 확인함. sequence_only는 HAP 서열/chain을 사용함. 모든 모드는 같은 window 저장 정책을 유지함.

**Input**

- Stage 09 HAP FASTA/chain
- Stage 10 두 HAP alignment, index, `S.realign.json`
- 기본 `WINDOW_SIZE=1,048,576`, seed, N/blacklist 정책

**Function**

- sample·HAP·contig·seed 기반 deterministic random offset으로 겹치지 않는 window를 만든다.
- N 포함 window와 blacklist overlap 기준을 적용한다.
- chain으로 reference 대응 coverage/blacklist를 검사한다. 주 window 표의 reference 좌표는 미정일 수 있으며 잔여 blacklist hit의 대응 좌표는 별도 표에 기록한다.
- HAP1과 HAP2 window는 각 개인 서열에서 독립 생성된다.

### Window 시작점·shift·끝 구간의 정확한 규칙

Stage 11이 후보/kept window 표를 만들고, Stage 12가 FASTA에서 같은 후보를 재계산해 Stage 11의 `kept=1` 행과 대조한다. 두 단계에서 서로 다른 random shift를 새로 추첨하지 않는다. Stage 18 RNA도 같은 HAP의 kept 구간표를 사용한다.

| 설정 | 현재 기본값 | 정확한 의미 |
|---|---|---|
| `WINDOW_SIZE` | 1,048,576 bp | window 길이와 stride. 1,000,000 bp가 아니다. |
| `WINDOW_SEED` | 42 | 아래 SHA-256 계산에 들어가는 seed. 실행마다 바뀌는 난수가 아니다. |
| `OFFSET_UNIT` | 빈 값 → window 크기 | offset 범위 `0 <= offset < U`. 숫자를 지정하면 `1 <= U <= WINDOW_SIZE`여야 한다. |
| `FIXED_WINDOW_START` | 0 | 1이면 U=1로 처리해 offset=0. 앞쪽 N을 제거한 원래 좌표까지 0으로 만드는 옵션은 아니다. 명시한 OFFSET_UNIT보다 우선한다. |
| `WINDOW_DROP_N` | 1 | Stage 11에서 실제 window 염기 중 non-ACGT가 하나라도 있으면 해당 후보를 제외한다. |
| `WINDOW_MAX_BLACKLIST_FRAC` | 0.01 | overlap 비율이 1% **초과**면 제외. 정확히 1%는 허용한다. |

현재 호출에서 SHA-256에 들어가는 문자열은 `"{seed}:{sample}:{HAP}:{contig}"`다. SHA-256 digest의 앞 8 byte를 big-endian 정수로 해석한 뒤 U로 나눈 나머지를 offset으로 사용한다. 샘플 이름과 HAP/chromosome 이름도 계산 입력이다. 같은 입력은 같은 offset을 만들며, 다른 입력의 결과가 반드시 서로 달라야 한다는 유일성 보장은 없다.

```text
U = OFFSET_UNIT 또는 WINDOW_SIZE  # FIXED_WINDOW_START=1이면 1
offset = uint64_big_endian(SHA256("seed:sample:HAP:contig")[:8]) mod U

left_N = 개인 FASTA 앞쪽에서 제거한 연속 N의 길이
candidate_start(i) = left_N + offset + i × WINDOW_SIZE
candidate_end(i) = candidate_start(i) + actual_length(i)
```

처리 순서는 다음과 같다.

1. FASTA를 대문자로 읽고 chromosome 양 끝의 연속 N을 제거한다. 좌표는 원래 개인 FASTA 기준으로 유지한다.
2. N-trim된 서열의 offset부터 window 크기 간격으로 후보를 만든다. window마다 별도 shift를 다시 뽑지 않는다.
3. trim된 시작부터 offset 직전까지의 앞쪽 서열은 이번 window 집합에 들어가지 않는다. 앞쪽으로 wrap하거나 별도 window로 보충하지 않는다.
4. 같은 HAP/contig 안의 후보는 겹치지 않는다. N/blacklist로 제외된 후보도 새 위치로 옮겨 대체하지 않는다.
5. chromosome 끝의 짧은 후보도 실제 길이를 `actual_length`로 기록한다. Stage 12의 서열 배열에서는 window 크기가 되도록 나머지를 특수 padding 염기 `P`로 채운다. WGS depth 배열도 padded 크기이며 padding 위치의 depth는 0이다. P는 실제 유전체 염기 N과 다르다. Stage 18 RNA window 배열은 실제 길이만 저장하므로 모델에서 padded DNA/WGS 축과 결합할 때 actual_length와 padding 처리를 확인해야 한다.
6. kept 행만 Stage 12/18 모델 구간으로 사용한다. HAP1/HAP2의 window 수·시작점이 다를 수 있다. 두 HAP의 같은 index를 동일 reference 위치라고 해석하면 안 된다.

### N·blacklist·좌표 대응의 선택 규칙

- non-ACGT 검사는 padded 길이가 아닌 실제 window 염기를 대상으로 한다. Stage 11 기본은 N뿐 아니라 R/Y 등 다른 non-ACGT도 제외한다.
- blacklist는 기본 `references/hg38_autosomes_blacklist_union.bed`다. SNV+indel 경로에서는 chain의 대응 block을 이용해 원래 reference의 blacklist와 개인 window의 겹침을 계산한다.
- `bl_frac = 개인 window 내 blacklist 대응 염기 수 / actual_length`다. padding 길이는 분모에 넣지 않는다. 중복 구간을 가진 사용자 BED는 중복 합산을 피하도록 union 처리된 입력을 준비해야 한다.
- `kept = N 조건 통과 AND bl_frac <= 0.01`다. 1% 이하 잔여 blacklist 염기를 서열에서 masking하거나 해당 위치 read/depth만 별도로 지우지는 않는다. kept window의 잔여 hit는 `windows_blacklist.tsv`에 기록한다.
- Stage 11의 chain coordinate coverage는 기록용이다. 0.95 미만이면 low-coverage 통계를 남기지만 이 값만으로 window를 제외하지 않는다. 이는 sequencing read depth와 다른 지표다.
- 현재 Stage 12 `personal_realigned` 경로는 이미 개인 좌표인 Stage 10 CRAM을 읽으므로 read projection은 해당 HAP 내 identity 좌표다. 이 경로의 coordinate coverage를 원래 GRCh38에 대한 매핑률로 해석하지 않는다.
- assembly-direct 선택 분기는 GRCh38 multi-chain blacklist 투영이 없어 reference blacklist를 명시적으로 비활성화한다. 현재 기본 VCF-consensus 경로의 정책과 구분한다.
- 주 `windows.tsv`의 `ref_start/ref_end`는 비어 있을 수 있다. blacklist 잔여 hit의 reference 대응은 별도 표로 읽어야 하며, 빈 값에서 GRCh38 좌표를 추측하지 않는다.

### Stage 11–12 설정 일치 및 선택 옵션의 제한

- Stage 12는 FASTA에서 만든 후보와 Stage 11 kept 행을 `(raw_start, actual_length)`로 맞추고 원래 kept 행 순서를 따른다. 후보 표의 window index와 compact의 재번호 index는 다를 수 있으므로 시작·끝·길이·순서로 비교한다.
- 두 단계의 seed/offset/window 크기가 달라 kept 행을 찾지 못하면 중단한다. 임의로 다른 구간으로 대체하지 않는다.
- **`WINDOW_DROP_N=0`은 비지원 옵션으로 config에서 조기에 거부한다.** 이전에는 Stage 11의 N-window keep과 Stage 12의 `max_n_ratio=0.0`가 충돌해 뒤늦게 실패했다. 기본 1의 결과는 유지한다. N 유지 실험은 별도 구현/승인이 필요하다.
- 크기·seed·offset·blacklist 기준은 모델/전처리 정책이며 보편 논문의 합격선이 아니다. 설정을 바꾸면 기존 window/Zarr 재사용 가능성도 다시 검증해야 한다. 이번 문서 보강은 값을 변경하지 않는다.
- 구현 근거: `window_index.windows_for_fasta`, `windowing.deterministic_offset/trim_terminal_n/make_windows`, `shared_hap_writer.prepare_hap_context/_apply_external_window_index`. 실제 실행 설정은 command/metadata와 `windows.tsv`를 함께 확인한다.


**Validation / stop**

- Stage 10 JSON의 sample, haplotype, output path, mapped fraction을 다시 검사한다.
- 두 alignment/index/QC가 모두 없으면 window를 만들지 않는다.
- duplicate key, 잘못된 좌표, 필수 contig 누락을 실패 처리한다.

**Output**

- `F/windows/windows.tsv`: contig, haplotype, window index, personal/reference 좌표, 길이, N, blacklist, kept 정보
- `F/windows/windows_blacklist.tsv`: 잔여 blacklist overlap 좌표
- `F/windows/windows.json`: schema, seed, size, offset, filter, HAP별 통계

**Next**

- Stage 12 compact와 Stage 18 `coverage_windows.zarr`는 이 `windows.tsv`의 HAP별 `kept=1` 행을 같은 순서로 사용한다. RNA 전장 coverage도 별도 보존한다.

## 12_compact_zarr.sh — 최종 WGS model-input compact 생성·검증

**모드별 입력과 출력**

- `full`: 아래 readset 경로를 사용함. Stage10의 개인 HAP CRAM을 decode하여 서열/readset/HAP depth를 저장함.
- `sequence_only`: HAP FASTA·chain·window에서 `sequence_4bit_acgtnp__windowed`를 생성함. WGS readset/depth를 만들지 않음.
- `pileup_feature`: Stage06 reference haplotag BAM + reference/decode FASTA + HAP FASTA/chain + window를 사용함. `hap_sequence_reference_pileup_v1`에 서열/pileup을 저장하며 HAP 재정렬 CRAM을 읽지 않음.
- 아래 **데이터 생성용/Function/readset 연결** 설명은 full 경로 기준임. 공통 입력 계약·필터·전수검증을 적용하되 payload별 실제 source를 구분함.

**Input**

**데이터 생성용**

- Stage 10 HAP1/HAP2 personal CRAM/index와 각각의 `target.fa`/FAI: read·CIGAR·개인 좌표·depth의 실제 원본
- Stage 09 HAP FASTA/QC: 모델 서열 및 target/reference 일치 검사
- Stage 11 `windows.tsv`: 개인 HAP 모델 구간

**QC·출처 추적용**

- Stage 06 haplotagged alignment: 파일 존재와 HP/PS 상태를 기본 최대 50,000개 record 표본으로 검사하고 source 이력을 기록
- Stage 09 chain: reference↔HAP 좌표 관계를 위한 연결·보존 자산. CRAM decode용 FASTA가 아님
- sample/project/platform/role metadata, 선택적 sequence VCF
- manifest의 `source_sample_id`: pipeline sample ID와 원본 BAM/CRAM·VCF donor 이름이 다른 경우에도 source trace가 실제 원본 이름을 사용하도록 한다.
- filter preset, MAPQ, compressor, chunk, validation/trace 설정

**Function**

- 각 contig의 HAP sequence를 4-bit encoding으로 저장한다.
- HAP별 read sequence, CIGAR/read·segment metadata, HP/PS·strand·개인 좌표·supplementary 여부와 per-base `uint32` depth를 저장한다. 모든 base quality와 부가 tag를 저장하는 원본 CRAM 보관본은 아니다.
- 새 BWA-MEM2/minimap2 alignment를 실행하지 않는다. Stage 06 BAM은 QC·출처에 사용하고 Stage 10 CRAM을 해당 HAP의 `target.fa`로 직접 decode한다. 두 좌표의 read/depth를 합치지 않는다. 현재 shell은 CLI의 선택적 haplotagging도 요청하지 않는다.
- short-read preset은 unmapped, secondary, supplementary, QC-fail, duplicate, MAPQ<30, sequence 없음 record를 model input에서 제외한다.
- long-read preset은 unmapped, secondary, QC-fail, MAPQ<30, sequence 없음을 제외한다. supplementary는 read/segment evidence로 보존하고 주 depth는 primary만 사용한다. supplementary depth는 별도 track이며 모델의 primary 선택은 metadata 계약을 따라야 한다. DUP flag만으로 제외하지 않는다.
- `full` 검증은 sequence, CIGAR, read metadata, depth, source SHA-256 multiset을 원본과 대조한다.
- 독립 trace validator가 compact→source 역추적과 변조 탐지를 수행한다.
- source trace의 `source_sample_id`에는 디렉터리 이름 `sample_id`를 무조건 복사하지 않고 manifest alias를 기록한다. 예를 들어 pipeline ID와 public donor alias가 다른 경우 원본 read 추적은 alias를 기준으로 검증한다.

### pileup_feature의 생성·투영·독립 검증

- 계산: reference 기준 primary base 관측에서12채널을 산출함. 생산 C++ CIGAR walker와 검증 HTSlib pileup 집계는 별도 구현임. 양 HAP가 같은 reference 위치에 대응하면 같은 관측을 사용하며 HP/allele별 tensor로 해석하지 않음.
- HAP insertion: HAP 서열은 보존함. `mapping_kind=2`이고 왼쪽 anchor의 generic insertion_ratio만 전달함. 삽입 allele 일치율이나 삽입 염기별 depth/BQ/base ratio는 생성하지 않음.
- 저장: `pileup.zarr/HAP1|HAP2/features`는 float32 12채널, depth/baseq_depth/supplementary_depth/max_deletion_length는uint32, mapping_kind는uint8임. offsets/lengths와 HAP 서열 window 순서를 유지함. 채널 정의는 [README](../README.md#reference-pileup-선택-모드-2026-11-23)를 따름.
- `MFM_PILEUP_PRODUCTION_BACKEND=auto|native|python`, `MFM_PILEUP_VALIDATION_BACKEND=auto|native|aligned_pairs` 선택 가능함. auto의 대체는 빌드/로드 불가에 한정하며 입력/집계 불일치를 숨기지 않음.
- 저장 배열은 window당 한 번 읽어 SHA/유한값/관측·삽입·padding mask와 source 값을 함께 확인함. reference block cache를 양 HAP에서 공유하고 전체 염색체 depth 배열을 적재하지 않음. 검증 범위는 전수 유지함.
- 샘플 CPU grant 안에서 염색체 worker를 실행함. 16CPU 예산에서는 부모1+최대15 worker이며 RAM 예산에 따라 실제 동시수가 작아질 수 있음. worker 기본 RAM예약4GiB/가상 주소공간 보호8GiB임. 두 값은 `MFM_PILEUP_WORKER_RAM_BYTES`/`MFM_PILEUP_WORKER_AS_BYTES`로 설정하며 주소공간은 예약 이상이어야 함.
- 같은 source/policy 지문의 완성 contig만 재검증 후 재사용함. 다른 payload를 덮어쓰지 않음. 최종 compact/source trace가 모두 통과해야 후속 QC/정리를 허용함.

### Read filtering의 정확한 기준

현재 shell은 `read_type`에 따라 `auto` preset을 선택한다. short는 `short_read_base_v1`, long은 `long_read_primary_supp_evidence_v1`다. 명시적 CLI preset이 read type과 다르면 실패한다. 아래는 낮은 수준의 `ExportConfig` 기본값만이 아니라 현재 Stage 12 production에서 최종 결정되는 정책이다.

| 검사 | Short read | Long read | 제외/유지 경계 |
|---|---|---|---|
| unmapped (0x4) | 제외 | 제외 | 정렬 위치가 없는 record |
| secondary (0x100) | 제외 | 제외 | 대안 정렬 위치. Zarr model read로 넣지 않음 |
| supplementary (0x800) | 제외 | evidence로 저장 | long의 primary depth와 별도 분리 |
| QC-fail (0x200) | 제외 | 제외 | upstream QC-fail flag가 설정된 record |
| duplicate (0x400) | 제외 | 이 flag만으로 제외하지 않음 | Stage 12가 duplicate를 새로 판정/mark하는 것은 아님 |
| MAPQ | 기본 30 이상 유지 | 기본 30 이상 유지 | `MAPQ < MIN_MAPQ`만 제외. 29 제외, 30 유지 |
| 원본 query sequence 없음 | 제외 | 제외 | SEQ를 읽을 수 없는 record |
| proper-pair | 필수 아님 | 필수 아님 | 현재 `require_proper_pair=False` |
| HP/PS 정보 없음 | 이것만으로 제외하지 않음 | 이것만으로 제외하지 않음 | HAP routing/선행 phase QC와 read-level filter는 다른 단계 |

현재 MAPQ는 숫자 비교다. SAM의 255는 “mapping quality를 제공하지 않음” 값이지만 이 필터에서는 30 이상이라 통과할 수 있다. RNA STAR의 MAPQ255 unique-only 정책과 WGS 필터를 혼동하지 않는다. [SAM flag·MAPQ·CIGAR 공식 규격](https://samtools.github.io/hts-specs/SAMv1.pdf).

`rejection_reason`은 unmapped → secondary → supplementary → QC-fail → duplicate → 선택적 improper-pair → low MAPQ → missing sequence 순으로 검사하고 첫 제외 이유를 반환한다. 여러 문제를 가진 read도 이 카운터에서는 첫 이유에만 집계될 수 있다. 제외 이유별 합계와 독립 flag 보유율을 같은 통계라고 보지 않는다.

### 적용하지 않는 기준과 pair/HP 정책

- Stage 12에는 별도의 절대 AS cutoff, HAP1/HAP2 상대 AS 승자 선택, NM/정렬 길이 비율 cutoff가 없다.
- base quality(BQ/평균 QUAL), 최소 read 길이, clipping 비율/percentile, read 서열의 N 비율, sample depth 균등화나 downsampling을 이 record filter에서 수행하지 않는다. read N은 저장 가능한 문자다. FASTA window의 non-ACGT 제외와는 다른 정책이다.
- 두 mate는 각각 alignment record 기준으로 필터된다. 한 mate의 MAPQ가 낮다고 상대 mate까지 자동으로 제거하거나 두 mate의 AS를 합해 선택하지 않는다. Stage 10의 완성 pair 추출·routing과 구분한다.
- Stage 10 `hap_specific`에서 이미 unknown/conflict를 제외했으면 그 결과가 입력으로 들어온다. 반대로 `all_to_both`의 미태그 read는 이 Stage 12 필터만으로 제거되지 않는다. HAP별 저장 파일 이름으로 HP를 덮어쓰지 않는다.
- `MIN_MAPQ=30`과 preset 선택은 현재 전처리 기준이며 SAM 규격 또는 모든 논문의 공통 cutoff가 아니다. 기록된 제외율과 downstream 목적을 보고 별도 검토한다.

### Window에 read를 연결할 때의 추가 처리

1. 해당 kept window와 겹치는 alignment만 fetch한다. kept window와 전혀 겹치지 않는 read는 model readset에 저장되지 않는다.
2. soft-clipped 염기를 제거한 mapped query 서열을 저장한다. hard-clipped 염기는 원래 BAM/CRAM SEQ에 없으므로 복원하지 않는다. M/=/X와 insertion의 query 염기는 보존한다.
3. clipping 제거 후 빈 서열이면 `excluded_empty_mapped_query`로 제외한다. window에 투영할 query/HAP segment가 없으면 `excluded_unprojectable`, 경계가 유효하지 않으면 `excluded_invalid_segment_coordinates`로 제외한다.
4. 저장 CIGAR도 clipping을 제거한 query 서열에 맞춘다. query/HAP 시작·끝이 read/window 실제 범위를 넘으면 writer/검증에서 실패한다. 이는 품질 cutoff가 아니라 배열/좌표 계약 검사다.
5. 한 read가 여러 window에 걸치면 각 window에 segment를 저장하고 같은 alignment key의 read 서열은 해당 HAP/contig readset 안에서 한 번 등록한다. R1/R2와 서로 다른 supplementary 정렬은 별도 alignment entry일 수 있다.
6. 이 등록 중복 제거는 반복 fetch/동일 alignment entry의 중복 저장 방지다. PCR duplicate 제거와 다르며 `all_to_both`의 두 HAP readset 사이에서 같은 분자를 전역 제거하는 것도 아니다.
7. read 서열은 A/C/G/T/N을 허용한다. 그 외 문자를 4-bit read에 저장하려 하면 현재 `fail` 정책으로 실패한다. HAP 서열 배열은 A/C/G/T/N/P를 표현하고 지원 밖 문자는 N으로 정규화할 수 있지만, 기본 kept-window 정책을 완화하는 의미는 아니다.

### Primary·supplementary·CIGAR depth 정의

| 항목 | Short read | Long read |
|---|---|---|
| `depth_segment_types` | (0,) primary | (0,) primary |
| `supplementary_depth_segment_types` | 없음 | (1,) supplementary |
| `model_segment_types` | (0,) primary | (0,) primary |
| supplementary read/segment 저장 | 제외 | evidence로 보존 |

`segment_type=0`은 primary, 1은 supplementary다. long read의 supplementary는 실제 read/segment 배열에 남을 수 있다. `model_segment_types=(0,)` / `primary_only` metadata는 모델이 주 입력을 선택할 때 지켜야 할 계약이지, 모든 supplementary 저장 행이 이미 삭제되었다는 뜻은 아니다. 이 문서 점검은 모델 dataloader의 실행까지 검증한 것은 아니다.

현재 WGS depth는 `cigar_ref_match` 방식이다.

- M, =, X 위치를 센다. X mismatch라고 해당 염기를 depth에서 제외하지 않는다.
- D(deletion), N(skipped reference)은 read 염기가 없는 위치이므로 WGS depth에서 세지 않는다.
- I(insertion)의 query 서열은 저장하지만 reference/HAP 염기 위치의 depth에는 별도 길이를 더하지 않는다. S/H/P도 depth를 늘리지 않는다.
- 겹치는 paired-end 두 mate를 fragment 하나로 합쳐 세는 보정은 없다. 유지된 각 alignment의 M/=/X가 해당 위치를 덮으면 각각 센다.
- long primary–supplementary overlap은 primary depth와 supplementary evidence depth로 나누어 기록한다. 두 track을 더하면 원래 목적과 달라질 수 있으므로 기본 model coverage로 합치지 않는다.
- chromosome 마지막 window의 depth 저장 길이는 padded 서열 길이와 같다. CIGAR 계산은 actual_length 안에서만 수행하며 P padding 위치는 0으로 저장한다. 저장 mean depth의 분모에 padding이 포함될 수 있어 실제 염기 범위의 depth 평균과 구분한다.
- WGS의 D 제외는 RNA Stage 18 `samtools depth -J`의 D 포함과 다르다. 두 depth의 계산 정의를 metadata와 함께 읽는다.

### 필터·window QC 및 오류 처리

- `export_config`에 실제 preset·MAPQ·flag·segment 정책을 기록하고, `filter_qc.json`/contig metadata에 유지·제외·projection·HP/PS·window 통계를 남긴다. fetch/chunk 통계는 같은 source record를 여러 번 관찰할 수 있어 고유 read 수와 구분한다.
- model read count는 필터 통과 여부뿐 아니라 kept window와의 overlap에도 좌우된다. 원본 전체 CRAM record count와 바로 같아야 하는 값이 아니다.
- read가 적거나 특정 window depth가 0이라는 이유만으로 그 window를 자동 제외하는 최소-depth 규칙은 없다. 다만 요청 HAP/contig에서 eligible window가 하나도 없으면 compact 생성은 실패한다.
- 내부 `full` 검사와 별도 source trace는 서열·read metadata/HP/PS·CIGAR·segment·depth를 대조한다. Stage 10 source CRAM과 정확한 HAP target FASTA가 기준이다.
- 불일치·유효하지 않은 배열/좌표는 해당 sample 실패와 후속 package/cleanup 차단으로 이어진다. 모든 옵션 조합이 검증됐다는 의미는 아니다.


**Validation / stop**

- 모든 요청 contig가 `full` validation PASS여야 manifest가 complete가 된다.
- trace `required`이면 모든 contig PASS 전에는 Stage 23/24로 갈 수 없다.

**Output**

  - `contig_metadata.json`

  - `hap_sequence.zarr`

  - long-read preset은 `supplementary_depth.zarr`

- work의 compact intermediate/log/timing

## Stage 18 — 전장 및 WGS-window RNA coverage 저장

**Input**

- Stage 17 marked HAP BAM
- Stage 15 target FASTA `.fai`
- Stage 11 `F/windows/windows.tsv`
- chr1–22, sample/HAP label

**Function**

- `18_coverage_zarr.py`는 chromosome별 전장 raw depth를 `coverage.zarr`에 저장한다.
- 같은 실행 안에서 전장 배열의 `kept=1` 구간만 잘라 `coverage_windows.zarr`를 만든다. samtools depth를 다시 실행하지 않는다.
- window store는 WGS 행 순서·index·personal/ref 좌표·window key·`windows.tsv` SHA-256을 기록한다.
- 실제 read filter는 STAR unique MAPQ 255, primary, QC-pass이며 supplementary는 제외한다. `-g 1024`로 duplicate는 포함하여 GTEx `bam2coverage.py` target과 맞춘다.

**Validation / stop**

## 20_hap_variants.py — ASE에 사용할 HAP 차이를 WGS read로 검증

**Input**

- Stage 09 `personal_fasta_qc.json`의 `refok_vcf`: HAP FASTA를 실제로 만든 phased VCF
- Stage 06 haplotagged WGS BAM/CRAM과 analysis reference
- Stage 09 HAP1/HAP2 FASTA, FAI, GRCh38→HAP chain
- GENCODE GTF, 처리할 autosome 목록

**Function**

- GENCODE exon ±1 kb에 있는 biallelic phased heterozygous SNV·MNV·indel을 고른다.
- 각 variant가 HAP FASTA에 실제 적용됐는지 FASTA 염기와 대조한다.
- GRCh38 좌표의 variant를 chain으로 HAP1/HAP2 개인 좌표 구간에 각각 연결한다.
- unmapped/secondary/supplementary/duplicate/QC-fail 또는 MAPQ<20 WGS read는 지지율 계산에서 제외한다.
- SNV·MNV는 read 염기를 직접 대조하고, indel은 반복서열 정렬 위치 차이를 고려해 같은 종류·길이 사건을 ±10 bp에서 확인한다.
- 기본 판정은 `validated`(depth≥10, alt fraction≥0.1), `unsupported`, `low_coverage`, `not_applied`다.
- contig 단위 process로 병렬 실행하며 `HAP_VARIANT_THREADS`는 동적 CPU lease를 넘지 않는다.

**Validation / stop**

- VCF, WGS alignment, reference, GTF, HAP FASTA/chain이 없거나 읽히지 않으면 Stage 20에서 해당 샘플만 실패한다.
- `hap_variants_qc.json`에 입력 VCF SHA-256, threshold, 종류·상태별 개수, 출력 SHA-256을 기록한다.
- alt fraction 0.1은 HG00096 HiFi exon het indel에서 0 부근 오류군과 0.4–0.5 지지군을 분리한 관측 기반 기준이다. 보편적 플랫폼 표준값이 아니라 현재 데이터 calibration 값이다.

**Output**

- `R/hap_variants.tsv`: reference variant, WGS 지지 수/비율, HP별 지지, HAP1/HAP2 좌표·allele, 인접 gene, 판정
- `R/hap_variants_qc.json` (`mfm_hap_variants_qc_v1`)

**Next**

## 21_allelic_counts.py — 검증된 HAP variant 위 fragment의 상대 AS로 ASE count 생성

**Input**

- Stage 17 HAP1/HAP2 RNA BAM
- Stage 14 HAP1/HAP2 `exons.bygene.tsv`
- Stage 20 `hap_variants.tsv`(필수)
- 기본 unique threshold `MAPQ>=255`

**Function**

- read가 아니라 query-name fragment를 한 표본으로 센다.
- primary만 사용하고 unmapped/secondary/supplementary/MAPQ0를 제외한다.
- 같은 fragment의 양 HAP에 공통으로 존재하는 mate의 STAR AS 합만 비교한다.
- STAR genomic-span length term을 AS에서 제거해 HAP indel span 차이가 승패가 되는 것을 막는다.
- `AS(H1)>AS(H2)`는 HAP1, 반대는 HAP2, 동점은 uninformative로 제외한다.
- 승리한 HAP 정렬이 Stage 20의 `validated` variant를 덮을 때만 allele 증거로 인정한다.
- 어느 HAP 정렬에서든 `unsupported`/`low_coverage`/`not_applied` variant를 덮으면 제외한다.
- 한쪽 HAP에만 정렬된 fragment도 그 HAP에서 validated variant를 덮을 때만 포함한다.
- 한 HAP에만 정렬된 fragment는 기본 포함하며 `--require-both-haps`는 민감도 분석용이다.
- 한 HAP에서라도 duplicate flag가 붙은 fragment는 두 HAP 표 모두에서 제외한다.
- 양 HAP에 공통으로 존재하는 gene만 세어 한쪽 annotation 소실로 생기는 구조적 편향을 막는다.
- query name의 deterministic BLAKE2b로 split-half를 만든다.
- 0<MAPQ<255 multimapper를 약한 allele 쪽에 보수적으로 더하는 sensitivity table을 만든다.

**Validation / stop**

- AS tag 없는 record는 비교에서 제외한다.
- fragment 단위·duplicate 합집합 provenance를 meta JSON에 기록한다.

**Output**

- `R/allelic_counts.tsv`: `gene_id, aCount(HAP1), bCount(HAP2), totalCount, ratio`
- `R/allelic_counts.split_half.tsv`: 두 deterministic half의 gene별 count/ratio
- `R/allelic_counts.both_haps.tsv`: 양 HAP에 모두 정렬된 fragment만 사용한 민감도 결과
- `R/allelic_counts.mmap_adjusted.tsv`: unique count, mmap count, 보수적 조정 ratio, `mmap_survives`
- `R/allelic_counts.meta.json` (`mfm_allelic_counts_meta_v5`): HAP variant SHA-256, 상태별 variant 수, 미검증/비정보 fragment 제외 수, fragment/duplicate/AS/routing 통계와 네 count TSV 각각의 SHA-256

**Next**

- Stage 22 CNV와 Stage 23 ASE QC

## 22_cnv_filter.py — WGS depth 기반 gene CNV filter

**Input**

- HAP1/HAP2 lifted exon TSV
- Stage 10 HAP1/HAP2 개인 좌표 WGS BAM/CRAM과 개인 FASTA
- 기본 최소 gene exon 길이 100 bp, 허용 `0.5<=rd<=1.5`

**Function**

- transcript 간 중복 exon을 gene별 합집합으로 병합한다.
- 개인 좌표 WGS alignment에서 `samtools bedcov`로 exon depth를 계산한다.
- HAP별 `rd = gene mean depth / 모든 gene mean depth의 중앙값`을 만든다.
- 두 HAP 중 하나라도 허용 범위를 벗어나면 CNV 의심 gene으로 표시한다.
- 필요한 HAP depth가 하나라도 없으면 `pass_cnv=0`으로 미평가 처리해 해당 gene의 학습 적격성에서 제외한다. CNV 이상을 확정한 의미는 아니며 샘플 전체를 중단하지 않는다.

**Validation / stop**

- exon/BAM/reference 수가 서로 맞아야 한다.
- median depth가 0이면 WGS alignment와 exon 좌표계 불일치 가능성으로 실패한다.
- 실제 `samtools bedcov` 기본 filter에 따라 UNMAP/SECONDARY/QCFAIL/DUP가 제외된다.

**Output**

- `R/gene_rd.tsv`: `gene_id, exon_bp, rd_hap1, rd_hap2, rd, pass_cnv`
- `R/gene_rd.tsv.meta.json`: 정책 revision, cutoff, HAP 수, 결측 처리와 HAP별 median depth, `gene_rd.tsv` SHA-256. Stage 23에서 같은 설정·내용인지 확인한다.

**Next**

- Stage 23. `RNA_CNV_FILTER=0`일 때만 명시적으로 skip한다. 1인데 필수 WGS 정렬이 없으면 Stage 22 실패 로그를 남기고 해당 샘플만 중단한다. Stage 23 재개에는 완료된 gene_rd.tsv를 사용할 수 있다.

## 23_ase_qc.py — validated-HAP 근거가 연결된 training-ready ASE label/QC

**Input**

- Stage 20 `hap_variants.tsv`
- Stage 21의 counts, split-half, both-haps, meta JSON과 multimapper-adjusted TSV
- Stage 22 gene RD TSV(활성 시)

**Function**

- 연속형 ASE ratio label과 binary ASE-positive label을 분리한다.
- exact binomial은 비교용으로, beta-binomial+BH FDR을 주 판정으로 사용한다.
- sample 단위 overdispersion `rho`를 ratio histogram의 weighted SSE로 추정한다.
- FDR은 `totalCount>=20` gene만 대상으로 보정한다. 연속형 label에는 FDR을 gate로 쓰지 않는다.

**Gene-level 기본 기준**

- `pass_depth`: total count >= 20
- `pass_split_depth`: split half 각각 count >= 5
- `pass_split_stability`: 두 split ratio 차이 <= 0.25
- `pass_cnv`: Stage 22의 HAP별 판정을 사용한다. 평균 RD로 재판정하지 않는다. 활성화된 검사에서 gene/HAP rd 누락은 제외하며 `cnv_status`에 기록한다. 필터 비활성화는 `disabled`로 구분한다.
- `continuous_eligible = depth + split stability + CNV 통과`
- `binary_ase_eligible = continuous eligible + beta-binomial FDR<=0.05 + split 방향 일치 + multimapper 보정 생존`

**Sample-level training-ready 기본 기준**

- Stage 21 schema/revision이 validated-HAP evidence를 사용한 v5여야 한다.
- duplicate가 ASE count에서 제외되어야 한다.
- overdispersion 적합에 6–2,500 depth gene이 최소 200개 있어 `rho` 추정이 가능해야 한다.
- informative fragment fraction >= 0.01
- continuous eligible gene >= 100
- split-half Pearson >= 0.30

**Validation / stop**

- 필수 sidecar 누락, read 단위 구형 count, 잘못된 provenance는 training-ready를 거부한다.
- Stage 21의 네 count TSV를 실제로 다시 hash해 `allelic_counts.meta.json`과 대조한다. Stage 22 CNV를 켰다면 CNV meta는 필수이며 `gene_rd.tsv`의 실제 SHA-256, policy revision, cutoff를 함께 대조한다.
- `ase_qc.json`에는 counts/split-half/both-haps/multimapper/meta/HAP variant와 선택적 CNV·CNV meta의 경로와 SHA-256을 기록한다. Stage 25와 cleanup guard는 이 연결을 다시 확인한다.
- QC 파일은 생성하지만 sample-level `sample_training_ready=false`와 reason code로 부적격을 명시한다.

**Output**

- `R/ase_qc.tsv`: gene별 count, ratio/CI, binomial·beta-binomial p/q, split/CNV/mmap/sensitivity, 적격성·reason
- `R/ase_training_eligibility.tsv`: 모델에서 바로 읽는 `sample_training_ready`, continuous/binary eligibility table
- `R/ase_qc.json` (`mfm_ase_qc_v3`): threshold, overdispersion, sample-level QC, 통계와 해석

**Next**

- Stage 24 metadata stamp와 Stage 25 full package validation

## 26_cleanup_intermediates.sh — PASS sample만 안전 cleanup

**Input**

- Stage 25 `final_package_validation.json`
- compact manifest/full validation, source trace, WGS/RNA 최종 산출물
- cleanup enable/dry-run/shared-assets 설정

**Function**

- validation schema, sample, mode, PASS 상태를 다시 확인한다.
- 최신 contract revision까지 맞는지 확인한다. 예전 PASS JSON만으로 삭제를 허용하지 않는다.
- Stage 09/final validation이 고정한 `permanent_assets.json`을 `verify`하고 final report에 기록된 manifest SHA-256과도 대조한다. cleanup 직전에 manifest를 다시 만들어 변경된 FASTA를 승인하지 않는다.
- WGS compact, 모든 contig, trace와 RNA 필수 산출물을 보수적으로 재확인한다.
- RNA full에서는 네 count TSV, HAP variant, CNV와 producer/consumer SHA-256을 대조함. coverage_only는 두 HAP signal/QC/지문을 검증하며 ASE/CNV 파일은 요구하지 않음. 최종검증 이후 evidence가 변경되면 stale로 판정해 정리를 거부함.

- `MFM_MODEL_ONLY_CLEANUP=1` 또는 비full payload는 `handoff.cleanup`의 모델 전용 정리를 사용함. FASTA·비압축 chain·windows·개인 BAM/CRAM·STAR index/FASTQ·sample work를 제거할 수 있음. window 원장·압축 chain·자산 manifest는 metadata에 보존함.
- full/MFM_MODEL_ONLY_CLEANUP=0은 기존 보수적 정리 경로를 사용함. 이 경우 개인 FASTA/windows/haplotagged 추가 정리는 `CLEAN_SHARED_ASSETS_ON_SUCCESS` 설정을 따름.
- 모델 전용 외부 정리는 `completion_cleanup`과 입력 소유권 정책을 따름. 샘플 전용 raw/index/개인 VCF/외부 work도 정리 대상이 될 수 있으며, 공유 reference/panel·다른 샘플·미등록 원본을 일괄 삭제하지 않음.
- 기존 외부 원본 보존은 `remove_owned_raw_inputs=false`만으로 충분하지 않음. 비full 출력에서 내부만 정리하려면 `CLEAN_INTERMEDIATES_ON_SUCCESS=1`, `MFM_MODEL_ONLY_CLEANUP=0`, `remove_owned_raw_inputs=false` 조합을 사용함. 상세는 [GUIDE](../GUIDE.md#7-검증재개정리) 참조함.

**Validation / stop**

- Stage 25 보고서가 없거나 FAIL이면 어떤 파일도 삭제하지 않는다.
- RNA full에서 `hap_variants.tsv` 또는 `hap_variants_qc.json`이 없으면 정리를 거부함. coverage_only에서는 해당 근거를 요구하지 않음.
- 허용된 `F` 하위 또는 output `_work` 하위가 아닌 경로는 unsafe target으로 거부한다.
- pair는 RNA 완료 전 WGS cleanup을 skip한다.

**기존 완료 sample 재검증**

- 이번 무결성 필드가 없는 기존 RNA output은 Stage 25에서 자동으로 신뢰하지 않는다. 배열·count 값을 임의 변환하는 migration 대신 Stage 18과 Stage 21–25를 다시 실행해 producer가 새 hash를 기록하게 한다. Stage 19도 coverage QC를 최신 Stage 18 결과와 다시 연결하려면 함께 재실행하는 편이 안전하다.

## 27_make_catalog.py — PASS sample catalog와 cohort 완전성 집계

## 7. 현재 확정된 RNA 산출물 계약

1. **Stage 19 summary**: `rna_realign_summary.json`이 canonical이며 `rna_qc.json`은 호환 alias다.
2. **Stage 23 ASE 상세 결과**: `ase_qc.tsv`, `ase_training_eligibility.tsv`, `ase_qc.json`을 보존한다. package validator는 eligibility·JSON과 validated-HAP provenance를 필수 검사한다.
3. **Stage 18/21/22 duplicate 정책**: Stage 18 coverage는 GTEx target에 맞춰 DUP를 포함한다. Stage 21 ASE와 Stage 22 CNV는 각각 fragment QC·copy-number QC 목적상 DUP를 제외한다.
4. **Stage 25→26 안전장치**: RNA package validation이 PASS이고 현재 HAP variant/count/ASE hash가 일치할 때만 cleanup backend를 호출한다.

## 8. QC 계약 수정 및 자체 threshold 감사

- Panel 다운로드 안내는 `PANEL_SOURCE_URL`, Stage 02/03의 실제 입력은 `PANEL_LOCAL_DIR`다. 기존 로컬 `PANEL_BASE`는 호환 alias이고 원격 URL 설정으로 자동 다운로드하지 않는다. 22개 VCF와 index는 사용자가 준비해야 한다.
- RNA coverage는 `-g 1024`로 DUP를 포함한다. `coverage_policy_revision`, 실제 `samtools_depth_args`, 입력 signature가 모두 일치할 때만 재사용하며 구형 duplicate-excluded coverage는 거부한다.
- CNV 수정은 ASE eligibility가 달라질 수 있다. 기존 완료 샘플을 자동 덮어쓰지 않는다. source BAM/CRAM, read count, RNA depth, 통계 검정 p/q 자체를 변경하는 작업이 아니다.
- 자체 cutoff와 무결성 검사는 다르다. reference/VCF REF/M5/좌표/chain/trace/sample ID 검증은 유지한다. WGS mapped와 RNA paired의 0.90은 보편 문헌 근거가 없는 과거 운영 참고선이므로 기본 `record_only`에서는 관측값·참고선 미만 여부만 기록한다. `strict`를 명시한 경우에만 과거 중단 동작을 재현한다. Illumina paired-primary fraction은 proper-pair 비율과 다르다.
- MAPQ≥30은 read 제외, N/blacklist 1%는 window 제외다. 모든 후보가 사라진 경우만 빈 출력 계약 때문에 실패한다. CNV 범위·split-half·정보량/유전자 수/상관계수 기준은 gene 또는 sample의 학습 적격성 표시이며 그 이유만으로 전처리/cleanup을 막지 않는다.
- 비율 QC는 전체 분포·제외 위치·read/depth/allele balance를 비교할 수 있도록 계속 보존한다. 현재 확인한 RNA input 3개(HG00096/HG00281/NA20503)는 paired=1.0이며, 이전 중단은 해당 0.90 기준 때문이 아니었다. 고정 공간 예산의 현재 기본은 `PREFLIGHT_MIN_FREE_GIB=0`이다.
