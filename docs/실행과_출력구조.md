# original 실행·출력·전달 구조

기준일: **2026-11-23**. 실행 예제·모드·정리 설정은 [GUIDE.md](../GUIDE.md), 단계와 도구는 [PIPELINE.md](../PIPELINE.md)를 따름.

## 1. 입력과 JSON 경로

- 주 입력 목록은 `manifests/preprocess_manifest.tsv`, 추가 read 파일 목록은 `manifests/read_files.tsv`임. 다운로드/내장 큐는 기관·배치별 선택 TSV를 사용하며 동일 donor가 여러 run 파일을 가질 수 있음.
- JSON의 `data_root`는 원본·개인 VCF·다운로드 receipt 저장소, `output_root`는 산출물 root, `state_root`는 큐/샘플 장부 root임. 세 경로를 같은 경로로 지정하지 않음.
- 상대 경로는 JSON 위치를 기준으로 해석함. 클라우드 복사본은 중앙 경로 자동 탐색을 하지 않으며 JSON의 경로를 사용함. dry-run에 표시된 최종 경로를 확인함.
- `--selection`은 한 기관·한 배치에 속한 목록임. 선택한 ID의 실제 원본 정보는 동결 master에서 가져옴. 여러 배치를 한 실행에 합치지 않음.

| manifest 정보 | 의미 |
|---|---|
| `alignment_path`, `read_files_manifest`, `wgs_source_format` | WGS BAM/CRAM/uBAM/FASTQ와 분할 run 파일의 관계임 |
| `source_sample_id`, alias/RG 정보 | pipeline ID와 원본 donor 이름의 대응임 |
| reference·VCF·donor ID | CRAM decode/analysis/VCF REF와 개인 서열 근거임 |
| `rna_path`, `rna_source_format`, `has_rna_pair` | RNA 입력과 pair 관계임. RNA 보류에도 관계는 보존함 |
| `project_id`, `data_group`, platform/read type | 프로젝트/기관/데이터 분류와 output routing 근거임 |
| `wgs_library_*`, `rna_library_*` | library amplification/PCR provenance임 |
| `*_input_bytes`, `known_input_total_bytes` | 다운로드·저장공간 계획 원장임. 모드에 따라 read 다운로드가 제외될 수 있음 |

## 2. 큐와 결과 layout

기본 배치 layout은 `<output_root>/<lab>_<batch>/` 아래에 결과를 생성함. `output_layout=run_root`이면 지정한 `output_root` 바로 아래에 생성함. 상태는 `<state_root>/<lab>_<batch>/`에 생성함. 직접 branch 실행은 `config_v2.sh`가 확정한 root를 사용함.

```text
<배치 결과 root>/
├── wgs/<project>/<sample>/                       # WGS-only
├── wgs_rna_pair/<project>/<sample>/              # pair: RNA를 보류해도 분류 유지함
│   ├── compact/<layout>/<contig>/
│   ├── rna_personal/<label>/                     # RNA 처리 시 생성함
│   ├── metadata/
│   │   ├── sample.json
│   │   ├── wgs_windows.tsv / wgs_windows.json
│   │   ├── wgs_windows_blacklist.tsv             # blacklist 주석이 있을 때
│   │   ├── reference_mapping/HAP{1,2}/*.chain.gz
│   │   ├── window_policy.json
│   │   └── cleanup_completed.json                # 모델 전용 정리 완료 시
│   ├── qc/final_package_validation.json
│   └── logs/stage_logs/
├── _work/<run-id>/<data-group>/<project>/<sample>/
└── _run_status/<run-id>/

<state_root>/<lab>_<batch>/
├── effective_config.json / selected_samples.tsv
├── samples/<sample>.json / <sample>.run.log
└── queue/status.json / 작업재개요청.json
```

실제 파일명·필수 산출물은 해당 payload와 완료 상태에 따라 달라짐. `individual_fasta/`, `haplotagged/`, `realigned/`, `windows/`, STAR index와 FASTQ는 계산 중 존재할 수 있으며 모델 전용 cleanup에서 제거 가능함. 날짜가 붙은 과거 출력 경로를 현재 모든 실행의 고정 목적지로 간주하지 않음.

## 3. WGS payload별 최종 모델 입력

| 모드 | layout | contig별 내용 |
|---|---|---|
| `full` | `COMPACT_LAYOUT_NAME`에 기록된 readset layout | `hap_sequence.zarr`, `readset.HAP1.zarr`, `readset.HAP2.zarr`, `depth.zarr`, 해당 시 `supplementary_depth.zarr`임 |
| `sequence_only` | `sequence_4bit_acgtnp__windowed` | `hap_sequence.zarr`, `windows.tsv`, contig metadata임 |
| `pileup_feature` | `hap_sequence_reference_pileup_v1` | `hap_sequence.zarr`, `pileup.zarr/HAP1`, `pileup.zarr/HAP2`, `windows.tsv`, contig metadata임 |

Pileup의 각 HAP group은 `features`(12채널 float32), `depth`, `baseq_depth`, `supplementary_depth`, `max_deletion_length`(uint32), `mapping_kind`(uint8), `offsets`, `lengths`를 저장함. HAP insertion/padding에 가짜 per-base 관측을 만들지 않으며, `mapping_kind`와 BQ 관측 depth를 함께 사용함. 채널 정의는 [pileup 상세 설명](전처리_상세.md#reference-pileup-선택-모드-2026-11-23) 참조함.

서열과 feature는 같은 개인 HAP window 순서를 사용함. window 원장의 `n_fraction`·`bl_frac`와 `metadata/reference_mapping/`은 학습 필터 선택 및 reference↔HAP 해석에 사용함.

## 4. RNA payload별 산출물

- 공통: `rna_personal/<label>/HAP1|HAP2/coverage.zarr`는 HAP 전장1bp signal, `coverage_windows.zarr`는 같은 signal을 WGS kept-window 순서로 자른 모델 입력임. 두 HAP BAM/QC·GENCODE lift·정책 지문을 확인함.
- `full`: `hap_variants*`, `allelic_counts*`, `gene_rd*`, `ase_qc*`, `ase_training_eligibility.tsv` 등의 근거를 추가함. WGS 변이 근거와 개인 HAP CRAM은 계산 중 필요함.
- `coverage_only`: ASE/CNV를 비적용으로 기록하고 signal/QC와 `rna_signal_manifest.json`을 검증함. 해당 TSV의 존재를 완료 요건으로 요구하지 않음.
- RNA 보류: metadata의 `completion_scope`·`rna_processing_status=deferred`로 표시함. DNA만 완료한 상태를 RNA 완료로 집계하지 않음.

## 5. 정리와 최종 완료 판정

- WGS-only Stage23→24, pair RNA Stage25→26 순서로 최종 QC 뒤 정리함. RNA가 실행되는 pair는 WGS 중간을 먼저 정리하지 않음.
- 모델 전용 정리는 `compact/`·최종 RNA Zarr/TSV·QC·metadata·로그와 압축 매핑을 보존함. 원본 FASTA/비압축 chain을 물리 파일로 영구 보존한다는 의미는 아님.
- 내부 중간 정리·외부 원본 정리는 별도 정책임. `MFM_MODEL_ONLY_CLEANUP=1`은 외부 정리를 호출할 수 있음. 기존 외부 raw를 보존하려면 [GUIDE의 설정 조합](../GUIDE.md#7-검증재개정리)을 함께 적용함.
- `final_package_validation.json.status=pass`와 정리 완료 시 `metadata/cleanup_completed.json.post_cleanup_validation.status=pass`를 확인함. 과거 PASS 또는 파일 존재만으로 완료 판정하지 않음.
- 모델 용량은 `handoff.cleanup.model_bytes` 기준 `compact/`와 RNA coverage Zarr/TSV의 파일 바이트 합계임. raw/중간/전체 폴더 점유량과 구분하고 GB=10^9, GiB=2^30을 명시함.

## 6. 전달 도구

| 도구 | 용도 |
|---|---|
| `scripts/build_portable_manifest.py` | 동결 registry → portable manifest/read-files/sample list 생성함 |
| `scripts/build_input_inventory.py` | 입력 포맷·pair·library provenance를 집계함 |
| `scripts/build_capacity_catalog.py` | raw URL 용량과 실측 compact를 바탕으로 추정함. payload/실측 조건 확인 필요함 |
| `scripts/build_stratified_shards.py` | 프로젝트·pair·플랫폼을 고려해 shard 생성함 |
| `scripts/download_shard.py` | shard 입력 전송·재개·크기/checksum 검증함 |
| `scripts/make_handoff_bundle.sh`, `scripts/make_sharded_handoff.sh` | 외부 서버용 코드·목록 bundle 생성함 |

과거 shard의 용량·ETA는 당시 payload와 실측에 종속됨. 새 모드의 파일 수·공통 자산·최종 용량은 선택 TSV와 config 기준으로 다시 계산함.
