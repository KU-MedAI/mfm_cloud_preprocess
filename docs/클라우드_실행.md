## 1. 코드·원본·공통 자산·결과를 구분함

- 코드 bundle: source/환경파일/다운로드 목록/문서/검사도구임. 동일 버전을 여러 노드에 배포함.
- 공통 자산: reference/FAI·phased panel/index·GENCODE임. [동봉 catalog](../manifests/공통자산.json)에57항목의 공개 URL·파생 규칙·size/SHA256가 있음. assets/manifest.json이 없으면 이 catalog를 사용해 필요한 누락 항목을 자동 준비함. 검증된 공유/노드 cache를 재사용 가능함. bundle에 있는 실물 데이터는 작은 blacklist 주석뿐임.
- 샘플 입력: donor별 BAM/CRAM/uBAM/FASTQ·개인VCF/index임. 기존 URL downloader 또는 사전에 검증한 로컬 파일을 사용함. 한 donor의 여러 run을 임의로 하나만 선택하지 않음.
- 결과: compact/RNA Zarr·window 주석·압축chain·QC·metadata·로그임. raw/임시파일과 구분해 내구성 있는 저장소로 회수함.

코드는 Linux/POSIX 파일·flock·원자적 rename·index 기반 random access를 사용함. Blob URI를 JSON의 data/output 경로에 직접 넣지 않음. 객체 저장소 전송은 AzCopy/스토리지 측 동기화 등 별도 전송으로 준비하고, 파일시스템 마운트는 위 계약을 별도 검증해야 함. 전송 credentials를 코드/manifest에 저장하지 않음.

## 2. VM에서 단일 큐로 처리

클라우드 처리 범위는 `--target`으로 선택함. 자동 선택하는 명단/설정은 다음과 같음.

| target | 선택 인원 |
|---|---:|
| azure_poc | 228명 |
| azure_main | 1,257명 |
| aws_main | 1,257명 |
| server | 470명 |

```bash
# 명단 전체 확인/실행임. 실제 동시수는 선택한 VM의 자원 설정을 따름.
bash run_pipeline.sh dry-run --target azure_poc
bash run_pipeline.sh run --target azure_poc
# VM별 한 명만 배정하는 예시임.
bash run_pipeline.sh run --target azure_poc --sample HG00308
```

`--config`가 없으면 target의 예제 JSON을 사용함. 각 VM의 경로/자원은 설정으로 지정함. target 전체 선택은 기존220명/10TB 제한을 받지 않으며 명단 전체 완료가 기준임. 실제CPU/RAM·디스크 보호는 유지함. target과 lab/batch/selection을 함께 지정하지 않음. 클라우드3프로필은 샘플16CPU·동시1·중간보존이며 루트의 자동동시수·모델전용정리 예제와 구분함.

- 이번 신규 설치 검증 대상: Linux x86_64임. ARM·Windows·macOS와 GPU runtime은 이번 검사 범위 밖임.
- 기본 OS 조건: Bash, Python 3.10 이상(설치 전 검사), curl, sha256sum/awk/grep 등 표준 도구가 필요함. Conda가 없을 때 bootstrap은 GitHub Miniforge installer와 SHA256를 받아 확인함.
- 접속 조건: 패키지 채널과 공개 입력의 HTTPS/FTP endpoint에 접근 가능해야 함. 폐쇄망은 사전 환경/데이터 반입이 필요함.
- 디스크 조건: POSIX 경로와 flock/rename/random access, 충분한 용량, native cache의 실행/라이브러리 매핑이 필요함. 기본 설치/상태 경로를 쓰는 코드 디렉터리는 쓰기 가능해야 함.
- 최초 설치와 공통/샘플 입력 준비는 자동 수행하더라도 실행시간·저장공간이 필요함. 코드 bundle에 대용량 입력이 들어 있다는 뜻은 아님.

1. 코드를 새 노드의 코드 경로에 복사하고 `python tools/check_cloud_package.py`로 확인함.
2. 기본 OS 도구를 확인함. `run_pipeline.sh run`은 jj_mfm이 없으면 Conda/Miniforge와 environment.yml의 환경을 자동 설치함. Conda가 이미 있을 때는00번 install-core로 미리 설치/보강 가능함. 인수 없는00번은 Clair3까지 설치하며 Conda 선행 설치가 필요함. 기존 서버의 env/GPU 바이너리는 bundle에 포함하지 않음.
3. 예제 JSON을 작업용 파일로 복사함. 경로와 RAM 운영 예산을 지정하고 doctor/dry-run의 실제 한도·샘플·입력을 확인함.
4. `run_pipeline.sh run`으로 실행함. 같은 노드에서 여러 샘플을 내장 큐가 처리하도록 local_jobs를 사용함.
5. 최종QC·cleanup 보고서와 출력 목록을 확인한 후 결과를 회수함. VM 종료 전에 내구성 저장소에 동기화가 끝났는지 확인함.

예시 경로는 다음과 같음. 용량은 원본+중간+최종의 동시 점유 피크를 고려해 결정함.

```json
{
  "data_root": "/mnt/mfm/raw",
  "output_root": "/mnt/mfm/output",
  "state_root": "/mnt/mfm/state",
  "bundled_assets_root": "/mnt/mfm/common_assets",
  "run_id": "cloud_pileup_run01",
  "cpu_pool_limit": "auto",
  "cpu_allocation_mode": "fixed_sample",
  "sample_cpus": 16,
  "local_jobs": "auto",
  "memory_limit_bytes": 274877906944
}
```

이는 기존 예제에 병합하는 경로/자원 예시임. 256GiB는 VM 선택을 확정한 값이 아니며, 실제 단계 RAM 예측과 실측이 예산을 만족하는지 확인해야 함. 운영예산이 부족한 단계는 대기/실패할 수 있으므로 샘플·HAP 동시수/CPU·버퍼를 검토함. sort의 -m은 전체 RAM 상한이 아님.

```bash
# 한 명: 실제 제공 목록에 속한 lab/batch/sample을 사용함.
bash run_pipeline.sh dry-run --lab medai --batch 001 --sample NA12878 --config my_config.json --executor local
bash run_pipeline.sh run --lab medai --batch 001 --sample NA12878 --config my_config.json --executor local

# 한 배치: 해당 selection에 있는 샘플 전체임.
bash run_pipeline.sh run --selection manifests/리드별/medai/001/long_read.tsv --config my_config.json --executor local
```

기존 lab/batch/selection 방식에서 selection을 주면 sample 필터로 더 좁히지 않음. 이 방식의 한 실행에는 한 기관/배치만 넣음. 새 분담 전체/개별 task는 target과 선택적인 sample로 지정함. 분담 lab은 데이터 목록의 식별자이며 클라우드 서버의 소속을 강제하지 않음.

공통 준비 계획만 확인하려면 코드 폴더에서 아래를 실행함. 이 명령은 폴더 생성/다운로드를 하지 않음. 실물 수집과 파생 FASTA/FAI 생성은 실제 run에서 필요한 순서대로 수행함.

```bash
python3 -m handoff.asset_restore --assets-root ./assets --dry-run
```

- Slurm 제공 예제의 `slurm.memory`는 샘플 array task당 `384G`(384GiB)임. 4Gbp reference·16CPU 계획에서 두 HAP STAR의 최대 예약량 합계와 부모4GiB·10% 여유를 수용함. 실제 RSS 또는 최적 VM 메모리를 확정한 값이 아니며 입력·버퍼·GPU 설정을 바꾸면 재검토함. `local` 실행의 RAM 상한은 기존 JSON 설정을 따름. 저장된 실행 설정이나 별도 사용자 JSON은 자동으로 덮어쓰지 않음.

## 3. Batch 등에서 샘플별 task로 처리

각 task의 코드·환경 준비는 동일함. 실행 인자는 위의 한 명 run 명령을 사용함. Azure SDK/Batch resource 생성 코드는 이 패키지 범위에 포함하지 않음.

- task마다 고유 state_root와 run_id를 사용함. 공유 디렉터리에 서로 다른 selection_fingerprint를 쓰지 않음.
- 같은 샘플/output을 두 task에서 중복 생성하지 않음. payload가 다르면 output/state를 별도 지정함.
- 노드별 CPU 풀을 분리함. 별개 노드의 PID/메모리를 하나의 lease 폴더에서 합산하지 않음. 한 노드에서 여러 독립 task를 동시에 실행하면 노드 자원 배분과 CPU 풀 경로를 함께 검토함.
- 코드가 예산을 정해도 VM/vCPU를 생성하거나 과금량을 예약하는 것은 아님. 실제 배정량과 CPU초/경과초·RSS·I/O를 구분해 보고함.
- task/VM이 종료되면 로컬 scratch의 데이터가 사라질 수 있음. 기존 코드의 단계 재개는 필요한 파일과 상태가 남아 있을 때 가능함. 노드 손실 뒤 자동 복구/Spot 적합성은 별도 중단·복원 시험이 필요함.

## 4. 재개와 보존

- target 전체 큐에서 한 샘플 복구: `bash run_pipeline.sh resume --target azure_poc --sample HG00308 --from-stage 01`임. 복구 요청 때문에 전체 큐의 선택 범위를 한 명으로 바꾸지 않음.
- 처음부터 단일샘플로 만든 작업의 복구는 그 상태폴더의 effective_config.json과 selected_samples.tsv를 `--effective-config/--selection`으로 지정함. 전체target과 단일작업의 상태키가 다르므로 구분함.
- 큐가 종료되었으면 원래 run 명령을 같은 선택으로 다시 실행함. 아래 기존 lab/batch 방식도 그대로 지원함.

```bash
# 실패 원인 해결 후, 같은 config/선택 범위에서 검토된 단계 재개 요청함.
bash run_pipeline.sh resume --lab medai --batch 001 --sample NA12878 --config my_config.json --from-stage 12
# 큐가 종료된 상태이면 동일 run 명령도 다시 실행함.
bash run_pipeline.sh run --lab medai --batch 001 --sample NA12878 --config my_config.json --executor local
```

기본 모델전용 정리는 최종QC와 source trace 뒤 내부 중간 및 소유 원본을 정리할 수 있음. 기존 외부 원본을 보존할 실행은 `CLEAN_INTERMEDIATES_ON_SUCCESS=1`, `MFM_MODEL_ONLY_CLEANUP=0`, `remove_owned_raw_inputs=false`를 비full 출력에 적용함. 전체 중간 보존은 CLEAN_INTERMEDIATES_ON_SUCCESS=0도 명시함. [GUIDE](../GUIDE.md#7-검증재개정리)의 설정 조합을 확인함.

정리 후 개인 FASTA/BAM/STAR index가 없을 수 있으므로 RNA만 추가 실행할 때 원래 reference/VCF/window 계약을 재생성·대조해야 함. 단순 파일 존재나 과거 PASS JSON만으로 성공을 가정하지 않음.

## 환경 자동 준비의 실제 호출

| 진입점 | 처리 |
|---|---|
| run_pipeline.sh run/prepare/worker/finish | handoff/environment.sh의 handoff_environment를 호출함 |
| Conda 없음 | Miniforge installer와 SHA256를 받고 확인한 뒤 설치함 |
| jj_mfm 없음 | environment.yml로 jj_mfm을 생성·활성화함 |
| jj_mfm 있음 | 필수 Python 모듈·도구·STAR2.7.11b를 검사함. 기존 환경을 자동 업데이트하지 않음 |
| run_pipeline.sh env install-core | 00_environment.sh install-core를 호출해 yml·requirements를 명시 설치/보강함. Conda가 먼저 필요함 |
| 인수 없는00번 | core와 선택 Clair3 환경을 함께 설치/보강함. Conda가 먼저 필요함 |
| doctor/dry-run/download --dry-run | 환경 설치 없이 계획만 확인함 |

2026-11-24 검증 전용 사본에서 Conda 없는 상태의 Miniforge→jj_mfm 설치와00번 install-all(core+Clair3)을 실제 수행해 통과함. 설치된 도구의 합성 입력 처리도 확인함. 자세한 범위는 [검증 결과](검증결과.md)를 참조함.

00번 설치는 TOOL_VERSIONS.tsv와TOOL_VERSIONS_CLAIR3.tsv를 현재 설치값으로 갱신함. 배포 파일 검사는 설치 전 bundle에서 수행하고, 실행용 사본과 배포 snapshot을 구분함.

신규 설치·공통 파일 다운로드는 실제 시간이 필요함. OS 기본 도구·네트워크·실행 가능한 디스크를 자동 제공하는 기능은 아님. 원격 VM을 만들거나 유료 배포를 실행하지 않음.

## 5. 현재 포함된 검증과 남은 확인

- 경로 독립성·VM RAM 상한·모드 분기·원본 기능 회귀·배포 해시/재포장 검증은 로컬에서 수행함.
- 실제 Azure SKU/디스크/네트워크에서 전체 샘플을 처리한 속도·메모리·I/O·과금은 아직 측정하지 않음.
- environment.yml은 기존 환경과 분리한 jj_mfm prefix에 실제 신규 설치함(162패키지). 이 환경에서 기본 도구/STAR 버전 검사를 통과함. 실제 Azure OS·선택 GPU runtime/driver 검증은 별도임.
- Blob/Azure Files 등 마운트의 flock/atomic rename/random I/O, task 종료 후 결과 회수, 노드 손실 재개는 실제 배포 구성에서 검증함.

## native cache와 회귀검사 환경

- native cache의 기본은 `$XDG_CACHE_HOME/mfm_native` 또는 `$HOME/.cache/mfm_native`임. `MFM_NATIVE_CACHE_ROOT`로 바꿀 때는 쓰기와 실행/공유라이브러리 매핑이 가능한 파일시스템을 사용함. noexec인 `/tmp`에 두면 C++ 바이너리 실행 또는 라이브러리 로드가 실패할 수 있음.
- 파이프라인 셸은 OMP/OpenBLAS/MKL/NumExpr 보조 스레드를 기본1로 두고 실제 병렬 계산은 샘플/단계 예산으로 관리함. 큰 BLAS 기본 스레드 수와 worker 주소공간 보호가 충돌하지 않도록 함.
- Python 테스트를 직접 실행할 때도 아래 환경을 명시함. 전체 pytest 환경이 없으면 제공 unittest 기반 검사부터 실행 가능함.

```bash
conda activate jj_mfm
export PYTHONPATH="$PWD:$PWD/src:$PWD/vendor/MFM-DNARNAFM"
export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1
python -m unittest discover -s tests -p test_cloud_portability.py
python -m unittest discover -s tests -p test_pileup_feature.py
```
